0Quick Start

Install the published CLI as a devDep in any PCF project. Two subcommands, no config files. (Or clone the repo if you want to contribute.)

Zero-install — run via npx. npm caches the package after first run, so subsequent invocations are instant.

Bash / PowerShell # From inside your PCF project (or any folder):
npx @pcfworkbench/cli start --path ./MyControl

# Or pin it as a devDep if you want lockfile control:
npm i -D @pcfworkbench/cli

First loop run on a fresh machine takes 60–80s while Fluent UI v9 caches; subsequent runs are 5–15s.

Launch the interactive harness UI in your browser. Pass --path for single-control mode or --workspace to browse a folder of controls.

Bash / PowerShell # Single control
npx @pcfworkbench/cli start --path ./MyControl

# Gallery mode — browse all controls in a folder
npx @pcfworkbench/cli start --workspace ./samples

Headless build → render → report cycle. Exits 0 on success with a deterministic report.json + screenshot. The AI / CI gate.

Bash / PowerShell npx @pcfworkbench/cli loop --path ./MyControl --out ./reports

Want to hack on the harness itself? Clone the repo and run the dev workflow directly.

Bash git clone https://github.com/jaduplesms/PCF-Workbench.git
cd PCF-Workbench/harness
npm install
npm run dev

3Network Conditioning

Simulate real-world network conditions to test offline-first patterns, degraded connectivity, and Mobile Offline Profile behavior.

How it works — mirrors real Dynamics routing

The WebAPI shim mirrors the real Dynamics 365 routing model: context.webAPI auto-routes between online and offline stores, while webAPI.online and webAPI.offline target specific stores directly. In Offline mode, online calls reject and auto-routing falls back to the local store. In throttled modes, an artificial delay is injected via setTimeout. A status badge shows the active network state; custom mode lets you set any latency in milliseconds.

10Resource Leak Detection Production guardrail

After destroy() is called, the harness reports resources that were not cleaned up — the leaks that kill Field Service Mobile performance over long sessions.

Event Listeners

Monkey-patched addEventListener tracks every registration on window, document, and the control container. Unmatched listeners flagged by type, target, and stack trace.

Timers

setInterval calls and long-lived setTimeout (> 5 s) tracked. Uncleaned timers in PCF keep controls alive across navigation — a major mobile battery drain.

Observers

MutationObserver, ResizeObserver, IntersectionObserver instances tracked. Unresolved observers hold strong references that prevent GC.

17CSS Isolation @layer pcf-control

Control CSS is loaded into a CSS layer so Bootstrap resets and global styles from one control can't break the harness UI or sibling controls.

How it works /* Harness Fluent UI styles — unlayered (highest priority) */
.harness-topbar { background: white; }

/* Control CSS loaded into pcf-control layer (lower priority) */
@layer pcf-control {
  * { margin: 0; } /* Bootstrap reset — won't escape */
  body { font-size: 12px; } /* scoped to control */
}

Harness Always Wins

Unlayered styles always take priority over layered ones via CSS cascade rules — controls can't accidentally restyle harness chrome.

Controls Still Work

Within the control container, layered styles still apply normally. Your body resets and global selectors work; they just don't escape.

21Date Rebase & Time Travel Just shipped

Test scenarios capture an anchor date. When a scenario is loaded, every date in its entity records is rebased relative to today — so a saved scenario stays meaningful months later instead of decaying into stale "yesterday's tomorrow."

Anchor + Offset Model

A scenario records the date it was saved as the anchor. Each entity record's date fields are stored as offsets from that anchor. On load, the harness rebases every offset onto today's date.

Why It Matters

A "today's bookings" scenario built in March still shows bookings for today in November. Bug repros stay reproducible. Demos don't go stale. Field Service scenarios always test the present.

Saved scenario {
  "name": "Today's bookings",
  "savedAt": "2026-03-15T00:00:00Z",
  "dateRebase": {
    "anchor": "2026-03-15",
    "mode": "relative"
  }
}

When you load this scenario today, every starttime, scheduledstart, and endtime in your data is automatically shifted by the same delta — preserving the original relative gaps between records.

Why PCF Workbench?

The pcf-scripts start test harness was designed to answer one question: "does my control load?" Workbench was built to answer every question that comes after.

The problem it solves

Every PCF team hits the same wall. The built-in harness shows the control in isolation on a desktop browser — but controls in production run on phones, with flaky networks, inside Mobile Offline Profiles, against real Dataverse schemas.

Standard pcf-scripts start Pain

  • One control at a time — no way to browse a project of 20 controls
  • No device emulation — you ship to mobile hoping it fits
  • No network simulation — offline-first is blind until production
  • No WebAPI — every test requires pushing to a real environment
  • No lifecycle visibility — re-render loops surface as "it feels slow"
  • No memory / leak detection — Field Service Mobile dies in the field
  • No reproducible scenarios — bug repros are tribal knowledge
  • Slow feedback loop — build, push, open form, reproduce, repeat

With PCF Workbench Win

  • Gallery of every control, searchable, with thumbnails & build status
  • Four device presets + CSS container queries for true responsive testing
  • Offline / Slow 3G / Fast 3G / Custom latency, applied to every WebAPI call
  • WebAPI mock with full OData $filter, $select, $orderby, paging
  • Lifecycle monitor with health checks for re-render loops and missing cleanup
  • Resource leak detection: listeners, timers, observers reported after destroy
  • Save / load / export test scenarios — ship bug repros with the PR
  • Hot reload on bundle.js — no deploys to iterate

Section 1 of 2 — Building

Build entire PCFs with AI — not just test them

PCF Workbench ships two Copilot CLI skills that pair up to drive the full requirement → code → render → verify → ship loop on your laptop. pcf-engineer authors and reviews the code, pcf-workbench runs the harness and reports back — in a tight feedback loop where the AI fixes its own mistakes before you ever push to Dataverse. See BUILDING.md for the full guide.

The senior PCF engineer in your terminal. Knows the official Microsoft Learn API surface plus the hard-won patterns Microsoft doesn't document.

  • Field-bound, dataset, and lookup patterns
  • Field Service Mobile / offline considerations
  • isAuthoringMode design-time UX (InfoCard-style previews)
  • Fluent UI v8 / v9 integration, lifecycle correctness, no leaks

pcf-workbench

Operates this harness. Picks the launch mode, wires test scenarios, drives the build → render → report loop, hands structured JSON back to the AI.

  • One-shot "render with scenario X and report what broke"
  • Headless acceptance gate after any non-trivial code change
  • Device / network emulation (desktop, tablet, mobile, 3G, offline)
  • Leak triage — diffs listeners/timers/observers across init/destroy
  • Build watcher — rebuild your sample, harness HMRs automatically
  • Scenario replay so regressions get caught the moment they regress

1. One-time setup

Clone the repo — both skills auto-load when you run copilot inside it. No install step.

# Power Platform CLI + Copilot CLI
dotnet tool install --global Microsoft.PowerApps.CLI.Tool
npm install -g @github/copilot

# Clone — skills in .copilot/skills/ auto-register
git clone https://github.com/jaduplesms/PCF-Workbench.git
cd PCF-Workbench

Optional — copy into your user-scope to use them in every workspace: Copy-Item -Recurse -Force .\.copilot\skills\* "$env:USERPROFILE\.copilot\skills\"

2. Scaffold a new control

mkdir samples\MyControl
cd samples\MyControl
pac pcf init --namespace YourCo --name MyControl `
             --template field --framework react `
             --run-npm-install

3. Plan first — don't jump to code

The single biggest predictor of a clean AI build is a written plan you've signed off on before any code is generated. Ask Copilot to produce two artifacts and stop:

  1. Design document — bound property, manifest properties, UX states (default / focus / disabled / error / empty), Fluent component choice, a11y notes, edge cases. You can write it yourself or co-author it with Copilot.
  2. Milestoned plan with todos — M1: manifest + skeleton, M2: render + bound value, M3: validation + a11y, M4: scenarios + headless gate. Each milestone has explicit acceptance criteria.

Review both, push back, iterate. Only then green-light the build. This catches half the bugs before a single line is written and gives you a checklist to verify against later.

PS C:\PCF-Workbench> copilot
> I want a MyControl in samples\MyControl that lets a user
> rate a record 0-5 stars, writing back to a Whole.None field.
>
> Before writing any code, co-author with me:
>  1. A short design doc (DESIGN.md) covering bound property,
>     manifest properties, UX states, a11y, edge cases
>  2. A milestoned plan (PLAN.md) with todos and acceptance
>     criteria per milestone
>
> Stop after the plan. I'll review and approve before you build.

Copilot drafts both files, you tighten them, then say "go". The skills now have an explicit contract to build against — not a vibe.

4. Build — then let the loop close itself

> Plan approved. Execute M1, then run the headless
> harness loop and report. Stop at the first failing
> milestone so I can review.

pcf-engineer writes the manifest + index.ts + React component per the plan. pcf-workbench builds it, runs each scenario headlessly, captures screenshots + JSON, and hands the result back. If anything fails, Copilot patches the code and reruns — ticking off the plan's todos as it goes. Loop until green — no Dataverse round-trip.

Iterate by extending the plan

> Add a new milestone to PLAN.md: support a "max length"
> manifest property read via context.parameters.maxLength.raw.
> Update DESIGN.md's UX states if it affects the error path,
> then build once I approve.

New work goes into the plan first. pcf-engineer bumps the manifest version and updates index.ts; pcf-workbench rebuilds and reruns scenarios. Saved scenarios catch regressions instantly.

Sample 3-line prompt — with plan-first baked in

> New dataset control in samples\PercentBar: each row is
> a horizontal bar where width = (row.value / maxValue) * 100%.
> Plan first (DESIGN.md + PLAN.md), wait for my OK, then build
> and screenshot 5 rows to confirm proportional.

Honest caveats

  • AI doesn't replace knowing the platform — garbage requirement in, garbage control out
  • Harness targets ~95% UCI parity — ribbon / XrmAddOn / a few offline FS APIs still need a real env
  • Bundle size and a11y are your call — harness flags them, AI fixes when asked, bar is yours

Use it with GitHub Copilot CLI

Already have a PCF that builds but doesn't render? Same loop, different entry point. The shipped pcf-build-loop skill lets Copilot CLI — or Claude, Cursor, or any agent that reads markdown skills — drive the harness, read structured JSON reports, and iterate until your control renders cleanly.

1. Install the skill (once)

Copilot CLI loads skills from ~/.copilot/skills/<name>/SKILL.md. Copy the shipped skill there:

# Windows PowerShell
$dir = "$env:USERPROFILE\.copilot\skills\pcf-build-loop"
New-Item -ItemType Directory -Force $dir | Out-Null
Copy-Item <workbench>\harness\docs\ai-loop-skill.md `
          "$dir\SKILL.md"

The skill file has YAML frontmatter (name, description, user-invocable, argument-hint) so Copilot CLI auto-registers it on the next session. You'll see it listed under available skills with these triggers: fix this PCF, iterate on this control, make this PCF render.

2. Open Copilot CLI in your PCF project

PS C:\repos\MyAwesomePCF> copilot

3. Just ask

> this PCF builds but doesn't render anything
> in the harness, can you fix it?

No need to remember CLI flags. The skill's trigger keywords match the intent, the agent picks it up, runs the loop, and follows the bounded refactor cycle defined in the skill.

What the agent does

  1. Runs npx pcfworkbench loop --path <your-control>
  2. Parses report.json against the published schema
  3. If summary.status === "pass" — reports success and stops
  4. If fail / warn — reads lifecycle.events, consoleErrors, leaks, webApi.errorCount to localise the bug
  5. Reads the failing source files, plans a minimal single-root-cause fix
  6. Applies the edit (you approve), re-runs the loop, repeats
  7. Hard-stops after 5 iterations and surfaces the latest report to you

Guardrails baked into the skill

  • Never edits harness/ sources — the harness is the fixture, the control is the unit under test
  • One root cause per iteration — no batching of unrelated fixes
  • If a harness shim is missing (logs.unimplementedCount > 0), the agent surfaces the gap rather than papering over it
  • Stops and asks you for direction after 5 unsuccessful iterations

Try it now

> Use the pcf-build-loop skill to run a clean
> build against samples\ConformanceTester\
> ConformanceTester and report

Should return pass against the shipped exhibit in ~3–15s end-to-end depending on whether the build is cached.

Works with anything that reads markdown skills. The same ai-loop-skill.md drops into Claude (Projects → Skills), Cursor (Rules), or any custom agent that takes a system-prompt fragment. The JSON schema is the durable contract — agents consume structured data, not stdout.

Run it in GitHub Actions PR-time gate

The same pcfworkbench loop command runs unattended in CI. A ready-to-use workflow at harness/docs/examples/pcf-loop.yml turns every pull request into a render-and-render-clean check — broken PCFs are caught before merge, not after a user reports a blank tile in production.

1. Drop the workflow in

Copy the example into your PCF project and edit three env values:

# in your PCF repo
mkdir -p .github/workflows
curl -o .github/workflows/pcf-loop.yml \
  https://raw.githubusercontent.com/jaduplesms/PCF-Workbench/main/harness/docs/examples/pcf-loop.yml

# edit these three:
#   PCF_PROJECT_DIR   ← folder with package.json
#   PCF_CONTROL_DIR   ← folder with ControlManifest.Input.xml
#   PCF_WORKBENCH_REF ← 'main' or a pinned commit SHA
git add .github/workflows/pcf-loop.yml
git commit -m "ci: add PCF build-loop check"

2. Commit a CI scenario important

Without a scenario the harness boots with manifest defaults — usually blank — so the loop just confirms "it didn't crash on an empty form". To assert real behaviour, save a scenario from the Scenarios panel, export it into test-scenarios.json, and commit it. Then set PCF_SCENARIO:

# in your PCF repo
# Scenarios panel → Save as "ci-smoke" → Export → save next to ControlManifest.Input.xml
git add test-scenarios.json

# in .github/workflows/pcf-loop.yml, set:
env:
  PCF_SCENARIO: 'ci-smoke'

The workflow auto-passes --scenario "$PCF_SCENARIO" to pcfworkbench loop, which appends ?scenario=ci-smoke to the harness URL. Property values, page entity, network, and device preset are all applied before the control mounts — exactly as if you'd clicked "Load" in the Scenarios panel.

3. Open a pull request

The workflow auto-triggers when a PR touches **/*.ts, **/*.tsx, **/ControlManifest.Input.xml, **/*.css, or **/test-scenarios.json. workflow_dispatch is also wired so you can run it on demand from the Actions tab.

4. Block merge on red

The workflow exits non-zero on warn or fail. Add it to your branch protection rules as a required check and broken PCFs cannot ship.

What runs on every PR

  1. Checks out your PCF and clones Workbench at PCF_WORKBENCH_REF
  2. Caches npm + Playwright browser binaries (~30s first run, ~5s after)
  3. Builds your control with npm run build
  4. Runs npx pcfworkbench loop --skip-build --path <control> --scenario "$PCF_SCENARIO"
  5. Harness auto-applies the scenario before mount (property values, page entity, network, device)
  6. Uploads report.json + screenshot.png as the pcf-loop-reports artifact (30-day retention)
  7. Posts a sticky PR comment (updated on every push) with a one-table summary
  8. Exits non-zero on warn/fail so the PR check turns red

Example PR comment

🤖 PCF Build Loop — ❌ FAIL
Render: ✅ rendered
Leaks:  ✅ none
Budget: ❌ fail
        ❌ avgRenderTimeMs 312 (fail >200)
Perf:   firstUpdateView: 180ms ·
        avgRender: 312ms · renders: 1

Cost & pinning

  • ~90s per run on ubuntu-latest — free for public repos; 2,000 min/month free on private repos
  • Pin PCF_WORKBENCH_REF to a SHA in production so upstream Workbench changes can't silently flip the check
  • No Dataverse, no Power Platform CLI, no licence — everything runs against the same mock surface the local harness uses
Same loop, same JSON, same answer. A green Workbench loop on your laptop is the same green loop in CI — if it passes locally with npx pcfworkbench loop, the GitHub Actions run will too. No CI-only flakiness, no environment drift.

M16Unified Data & Metadata Access Layer

L Up next

Make live-vs-mock a single seam at the data layer so every feature (Form seeding, lookups, webAPI shim, DataPanel, metadata) is source-agnostic — it asks a provider, the provider routes to the local store or the live org. Reads already route through data-store.getEntityData and metadata shares one store; this milestone removes the remaining hand-written per-feature branches (esp. the 5 CRUD branches in web-api.ts) and makes metadata ride the same seam.

  • Phase 0 — determinism: applyScenarioToStore always sets dataSource (absent ⇒ mock) so a stale persisted live can't leak onto a mock scenario (the InfoCard dv-proxy bug)
  • Phase 1: extract records + metadata provider interfaces wrapping today's mock (data-store/mock OData) and live (dv-client) impls; route once by dataSource; no behaviour change
  • Phase 2: migrate web-api.ts CRUD (createRecord:448, deleteRecord:503, updateRecord:554, retrieveRecord:612, retrieveMultipleRecords:721) onto records; add ensureMetadata(entity) that Form seeding + lookups call so schema is present in both modes
  • Phase 3: re-seed the form on dataVersion so live page-record arrivals refresh it; surface data provenance (mock vs live, snapshotted vs inferred)
  • Network-conditioning stays a decorator on top of the provider (online/offline latency independent of source)
